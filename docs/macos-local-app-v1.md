# macOS local app v1

**Status:** proposed implementation specification
**Scope:** macOS only; direct distribution; an additional local deployment option
**Depends on:** [PR #41](https://github.com/swiknaba/digitaltwin/pull/41), which replaces the legacy Mattermost/Herdr stack with OpenCode, Commander, and Kirei FutureTasks.

## Decision

Ship `DigitalTwin.app`: a signed and notarized macOS application built from the
standard Electron-based OpenCode desktop shell with the maintained Commander patch
from PR #41. This is an installable Electron app, not a replacement Swift/AppKit UI.
The application starts a small, private local service group for Kirei FutureTasks
and PostgreSQL. It does not require Docker Desktop, a VM, a separately installed
database, a LaunchAgent, or a separate server for this local bundle.

This adds a local deployment choice. It does not remove, replace, or reconfigure
the existing server deployment; its infrastructure, networking, database, backup,
and operator ownership remain separate.

The app owns its children while it is open. A due task that becomes due while the
app is closed remains durable and is reconciled when the app next starts; v1 does
not claim background delivery while the user has quit the app. An always-running,
opt-in LaunchAgent is a separate future product decision, not an implicit install
side effect.

Use separate `arm64` and `x64` release artifacts first. Do not depend on Rosetta,
and do not make a universal bundle a v1 requirement.

## Why this shape

The current `main` branch is the retired Docker/Mattermost/Herdr product: its
Compose file starts a Linux/AMD64 Runtime, Mattermost, Kirei, and PostgreSQL. That
is not an installable native macOS application. PR #41 deliberately removes that
chat/runtime stack and makes OpenCode operator-managed, with Kirei retaining only
durable future commitments. This specification is therefore intentionally stacked
on the merged outcome of PR #41; it does not package the old Compose graph.

OpenCode v2.0.27 at `1f4d07a4a519185955ae8ab2ea3607805509e386` already provides
the appropriate desktop foundation. Its `packages/desktop` package uses
`electron-builder`, bundles its CLI outside `app.asar`, declares a hardened runtime
and notarization, and has updater integration. The Commander patch must remain a
reproducible patch set against that exact source revision until it is upstreamed or
re-pinned and revalidated.

## Product boundary

```text
DigitalTwin.app (OpenCode Electron main process)
├── OpenCode renderer + maintained Commander extension
├── OpenCode CLI/service (existing desktop lifecycle)
└── DigitalTwin local supervisor
    ├── PostgreSQL (private Unix socket; app data directory)
    └── Kirei web + worker (loopback/private transport only)
```

The renderer continues to use the standard OpenCode desktop/session APIs. It does
not receive database credentials, a PostgreSQL connection string, or a general
sidecar control API. Commander keeps PR #41's normal OpenCode session identity and
operator-selected neutral workspace/agent model.

Kirei remains the sole owner of FutureTasks records, due-job execution, delivery
keys, and migrations. OpenCode owns project sessions, prompts, agents, and their
provider authorization. There is no Mattermost, Herdr, Docker socket, browser
credential bridge, or private renderer socket control plane in this product.

## What the application packages

| Item | v1 treatment |
| --- | --- |
| OpenCode Desktop and CLI | Build the pinned upstream desktop source plus the generated Commander patch set. Preserve the upstream CLI's resource placement and existing desktop service lifecycle. |
| Commander extension and gate plugin | Include only the PR #41 sources generated by its preparation scripts; never copy an operator's config, plugin state, provider login, or OpenCode profile into the app. |
| Kirei FutureTasks | Package a pinned Ruby runtime, the locked Kirei bundle, app code, and typed migration/health entrypoints as a private executable resource. It is not exposed as a user-managed web service. |
| PostgreSQL | Package one pinned PostgreSQL distribution per CPU architecture, including `initdb`, `postgres`, `pg_ctl`, and required dynamic libraries. No Homebrew/Postgres.app dependency. |
| Notices and provenance | Generate a machine-readable component manifest (name, version, source revision, SHA-256, license/notice location, architecture) and a human-readable `THIRD_PARTY_NOTICES` file in the app/resources and release archive. |

The release gate must inventory every shipped native executable, framework, Ruby
gem, JavaScript dependency, and PostgreSQL file. OpenCode is MIT licensed; its
license must travel with the derived app. The legacy Runtime's proprietary Claude
Code dependency and its incomplete transitive-license audit are explicitly out of
scope. A component without redistributable terms or a complete notice path blocks
the release rather than being silently downloaded on a user's machine.

## Local data and service lifecycle

All mutable data is per macOS user and never lives inside the signed application
bundle:

| Location | Contents | Backup/deletion rule |
| --- | --- | --- |
| `~/Library/Application Support/DigitalTwin/OpenCode` | DigitalTwin-owned OpenCode desktop profile, Commander storage, and CLI state | Retain across app updates; do not read or modify the user's global OpenCode profile. |
| `~/Library/Application Support/DigitalTwin/postgres` | PostgreSQL cluster and Kirei database | Migration creates a verified, versioned local backup before an irreversible schema or PostgreSQL-major change. |
| `~/Library/Application Support/DigitalTwin/runtime` | Unix socket directory, PID/lock files, generated local-only configuration, bounded logs | Create with owner-only permissions; remove stale sockets/PIDs only after verifying their owner and process identity. |
| `~/Library/Caches/DigitalTwin` | Download cache and disposable diagnostics | Safe to clear from the app's support screen; never required to preserve FutureTasks. |

First launch creates the directories with owner-only permissions, initializes an
empty PostgreSQL cluster, creates a dedicated Kirei role/database, runs migrations,
then starts Kirei. `initdb` creates the cluster in an explicit data directory and
`pg_ctl` has explicit start/stop semantics, so both actions are supervised rather
than delegated to shell startup files. [PostgreSQL documents these lifecycle
operations](https://www.postgresql.org/docs/current/app-initdb.html) and
[controlled start/stop behavior](https://www.postgresql.org/docs/current/app-pg-ctl.html).

PostgreSQL must accept only a private Unix-domain socket in the owner-only runtime
directory, with no LAN listener. Kirei must bind only to loopback or its own private
transport and receive an app-generated local connection value. The supervisor passes
only the minimal environment needed by each child, uses executable paths rather
than a shell command string, captures bounded logs, and treats unexpected child exit
as visible degraded state. It retries a crash at most once automatically; repeated
failures require a user-visible repair action and diagnostic export.

On quit, the app stops Kirei first and PostgreSQL with `pg_ctl stop` using a bounded
grace period. On the next start it first verifies the lock/PID and database
consistency, recovers an interrupted PostgreSQL shutdown if needed, starts the
services, and lets Kirei reconcile pending/due executions through its existing
idempotency rules. The app never kills a process merely because a matching name
exists.

v1 does not provide full-disk encryption beyond the user's macOS account and any
system volume encryption they enable. It must state this plainly in the product UI.
Local database authentication material and FutureTask capability material are
generated per installation, never committed, never sent to the renderer, and are
restricted to the app-owned runtime configuration. The design is not a protection
boundary against another process already running as the same macOS user.

## Local bundle and existing server deployment

The macOS bundle supports local mode only in v1. It is selected by the installed
application, has no host/port form, and is not an operator setting that can
accidentally point at a remote Kirei or PostgreSQL instance.

The existing server deployment remains a separate supported product path and is
unchanged by this specification. A future *server-connected mode in this macOS
bundle* is deferred: it requires a separately specified authenticated transport,
certificate/identity handling, database ownership, backup/retention, upgrade
compatibility, and a deliberate export/import or migration protocol. The v1 app
must not offer a misleading "connect to server" field or silently fall back to a
remote endpoint.

## Packaging, signing, and updates

Distribute directly as a DMG containing `DigitalTwin.app`, not through the Mac App
Store in v1. The product needs the standard OpenCode desktop's native child-process
and developer-workspace behavior; this is a poor fit for a first App Sandbox
submission. Reassess a separate Mac App Store variant only after its sandboxed
constraints are designed and tested. Electron notes that Mac App Store applications
need the MAS build and App Sandbox support.

The release pipeline must:

1. Build each architecture on macOS from the pinned source, lockfiles, sidecar
   manifest, and generated Commander patches.
2. Sign every nested executable, framework, helper, CLI, PostgreSQL binary, and
   app bundle with the Developer ID identity; validate signatures before packaging.
3. Enable the hardened runtime and use the narrowest entitlements that OpenCode and
   the bundled CLI actually require. Do not inherit the CLI's broad dynamic-loader
   exceptions for Kirei or PostgreSQL without a documented, tested need.
4. Submit the final DMG/ZIP with `notarytool`, staple the accepted ticket, and run
   `spctl`/fresh-user launch checks. Apple's notarization guidance requires valid
   signatures and hardened runtime for Developer ID distribution; Electron likewise
   describes signing followed by notarization for macOS releases.
5. Publish a signed release manifest plus checksums, notices, SBOM/provenance
   records, and the current OpenCode/Kirei/PostgreSQL source revisions.

The DigitalTwin app must use its own bundle identifier, release channel, update
feed, and signing identity; it must never subscribe to the upstream OpenCode update
URL. Reuse Electron's supported macOS updater integration only after the app is
properly signed. The update feed must use HTTPS, architecture-specific artifacts,
versioned hashes/sizes, and a user-visible "download/restart" choice. Electron's
macOS updater requires a signed app and can verify declared update hashes before
unpacking. [Electron's updater documentation](https://www.electronjs.org/docs/latest/api/auto-updater)
describes those requirements.

An application update may contain a sidecar upgrade, but it may not silently
replace mutable data. Before starting a new Kirei/database schema, the supervisor
must take a local backup, validate the migration, retain rollback diagnostics, and
show an actionable failure state. Downgrades across an applied migration are not
supported unless a later release adds an explicit, tested restore path.

The app should default update checks to off until the user enables them, because a
check is an outbound network request. Provider/Git requests occur only after the
user completes the standard OpenCode configuration and uses a feature requiring
them. The test matrix must verify there is no non-loopback listener and record
actual macOS firewall, Gatekeeper, and network-warning behavior on clean test Macs;
do not promise that macOS will never display a prompt.

## Alternatives considered

| Approach | Decision | Reason |
| --- | --- | --- |
| Native supervised sidecars | **Use for v1** | Delivers one application and a controlled local data lifecycle without a separately installed platform. |
| Docker Desktop/Colima/VM | Do not use inside the local bundle | Easy to reuse the present Linux Compose files, but requires another app/VM, has different volume and networking semantics, consumes more resources, and fails the one-installable-app goal. Existing server/developer deployments remain separate. |
| A permanent user LaunchAgent | Defer | Needed only for delivery while the UI is closed. It adds persistence, update, repair, and uninstall obligations that are unnecessary for the first local app. |
| Replace PostgreSQL with SQLite | Do not use | It changes Kirei's persistence contract and migration behavior. Packaging PostgreSQL is substantial but bounded; a database rewrite is a separate product change. |
| Bundle the legacy Mattermost/Herdr Runtime | Do not use | It conflicts with PR #41's deliberate simplification and carries Linux/AMD64, provider, license, and socket boundaries that are outside the new product. |

## Delivery sequence

1. **Finalize PR #41 and freeze the baseline.** Merge the OpenCode/Commander/Kirei
   simplification, reproduce its generated patch preparation from the exact OpenCode
   revision, and record its release manifest.
2. **Native packaging spike.** On one architecture, package PostgreSQL and a locked
   Kirei runtime as app resources; prove first-launch initialization, migrations,
   graceful shutdown, crash recovery, and an unmodified user-global OpenCode/XDG
   profile. This is not a distributable release.
3. **Local-app integration.** Add the main-process supervisor, restricted child
   environment, local status/repair UI, backup-before-migration, and acceptance
   tests for Commander persistence plus due-task recovery after app restart.
4. **Release hardening.** Repeat the integration on `arm64` and `x64`, generate
   notices/SBOM/provenance, sign and notarize, exercise the updater on a clean user,
   and document uninstall/data-export behavior.

Each stage must stop on a failed native packaging, signature, license, migration, or
data-recovery check. A passing Docker test is useful development evidence but does
not substitute for a native macOS release check.

## Acceptance criteria

- A clean `arm64` and a clean `x64` macOS user can drag-install one signed,
  notarized `DigitalTwin.app` and run it without Docker, Homebrew, PostgreSQL, or a
  separate OpenCode install.
- The local bundle does not modify, stop, or depend on an existing server deployment;
  server operation remains independently documented and testable.
- First launch initializes only DigitalTwin-owned paths, starts OpenCode, PostgreSQL,
  Kirei web, and Kirei worker, and reports useful health/error state. It changes no
  global OpenCode/XDG configuration and imports no existing credentials.
- Commander has the PR #41 persistent global conversation behavior through project
  switch, panel close/reopen, desktop restart, send/stream/cancel/reconnect, and
  native-subagent follow-up provenance.
- A FutureTask created locally survives app quit, forced sidecar termination, and
  restart. Duplicate delivery/retry protections remain intact; a task due while
  closed is reconciled after restart, not claimed as background delivered.
- The release has no listening LAN port, no Docker/VM/LaunchAgent installation, no
  shell-interpolated child command, and no renderer access to database or provider
  secrets.
- The signed app, all nested code, DMG/ZIP, and first update pass signature,
  notarization, Gatekeeper, and clean-machine upgrade checks. The release includes
  complete notices and a verified component manifest.
- Data survives ordinary application update. A deliberately injected failed
  migration leaves a recoverable pre-migration backup and a clear repair path.

## Open risks and decisions needed before implementation

- A complete redistributability and license audit is required for the Ruby runtime,
  native gems, PostgreSQL binaries/libraries, Electron dependencies, and every
  OpenCode dependency. The legacy repository already records that its broader
  Runtime audit is incomplete; it cannot be reused as release proof.
- Kirei's current production bundle is Linux-container oriented. Creating a pinned,
  reproducible macOS Ruby/native-gem build and deciding its minimum supported macOS
  version are substantial work, not a configuration-only change.
- PostgreSQL major upgrades, backup size/retention, data export, and destructive
  reset UX need an owner before public release.
- Direct distribution needs an Apple Developer Program team, Developer ID signing
  material, and notarization credentials held in release infrastructure—not Git or
  the app image. These are external release prerequisites, not reasons to embed
  secrets or relax the design.
- No live OpenCode provider authorization, agent model run, or authenticated Kirei
  delivery is claimed by this specification. Those remain explicit operator/runtime
  acceptance checks after the native local lifecycle is proven.
